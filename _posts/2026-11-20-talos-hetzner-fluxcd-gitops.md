In **[Part 1]({% post_url 2026-11-19-talos-hetzner-bare-metal-cilium %})** we installed Talos Linux on a Hetzner dedicated server, bootstrapped Kubernetes, and set up Cilium as the CNI and kube-proxy replacement.

This part is about what comes *after* the cluster is up:

- 👉 **GitOps with FluxCD**
- 👉 **managing everything through Helm, including Cilium itself**
- 👉 **HTTPS via cert-manager and the Gateway API**

The goal is to keep the Talos philosophy all the way up the stack: **immutable nodes, declarative configuration, and no manual `kubectl` drift.**

## Why FluxCD?

FluxCD fits Talos well:

- You never touch the nodes. Talos doesn't even let you.
- You never install anything imperatively on the cluster.
- Everything lives in Git, with a full history of who changed what.
- Disaster recovery comes down to "point a new cluster at the repo".

Once Flux is bootstrapped, **Git becomes your cluster's control plane.**

## Repository Layout

We use a layout based on the official [flux2-kustomize-helm-example](https://github.com/fluxcd/flux2-kustomize-helm-example). Infrastructure and apps are kept separate, and so are *controllers* (things that install CRDs) and their *configs* (things that use those CRDs):

```text
talos-k8s/
├── clusters/
│   └── talos-hetzner/
│       ├── flux-system/          # generated by flux bootstrap
│       ├── infrastructure.yaml   # Flux Kustomizations for infra
│       └── apps.yaml             # Flux Kustomization for apps
├── infrastructure/
│   ├── controllers/              # HelmReleases: cilium, cert-manager, ...
│   └── configs/                  # ClusterIssuer, Gateway, IP pools, ...
└── apps/
    └── talos-hetzner/            # your workloads
```

Why split controllers and configs? A `ClusterIssuer` can't be applied until cert-manager has installed its CRDs. If both sit in the same Kustomization, the first reconcile fails. Splitting them lets Flux apply them in order.

## Bootstrapping FluxCD

Create a GitHub personal access token with repository permissions and run the bootstrap from your local machine:

```bash
export GITHUB_TOKEN=<YOUR_TOKEN>

flux bootstrap github \
  --token-auth \
  --owner=<YOUR_GITHUB_USER> \
  --repository=talos-k8s \
  --branch=main \
  --path=clusters/talos-hetzner \
  --personal
```

This command:

1. creates the repository if it doesn't exist yet
2. installs the Flux controllers into the `flux-system` namespace
3. commits its own manifests to `clusters/talos-hetzner/flux-system`
4. starts watching that path

From here on, **every change to the cluster is a Git commit.**

## Wiring Up the Layers

Flux only knows about `clusters/talos-hetzner`. We tell it about the other directories with Flux `Kustomization` objects and use `dependsOn` to set the order:

```yaml
# clusters/talos-hetzner/infrastructure.yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: infra-controllers
  namespace: flux-system
spec:
  interval: 1h
  retryInterval: 1m
  timeout: 5m
  sourceRef:
    kind: GitRepository
    name: flux-system
  path: ./infrastructure/controllers
  prune: true
  wait: true
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: infra-configs
  namespace: flux-system
spec:
  dependsOn:
    - name: infra-controllers
  interval: 1h
  retryInterval: 1m
  timeout: 5m
  sourceRef:
    kind: GitRepository
    name: flux-system
  path: ./infrastructure/configs
  prune: true
```

```yaml
# clusters/talos-hetzner/apps.yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps
  namespace: flux-system
spec:
  dependsOn:
    - name: infra-configs
  interval: 10m
  retryInterval: 1m
  timeout: 5m
  sourceRef:
    kind: GitRepository
    name: flux-system
  path: ./apps/talos-hetzner
  prune: true
```

`wait: true` on the controllers means "don't call this layer ready until every HelmRelease in it is healthy". That is exactly what the configs layer needs to wait for.

## Managing Helm Charts with Flux

Flux uses two CRDs for Helm:

- **`HelmRepository`**: where charts come from
- **`HelmRelease`**: which chart to install, which version, and with which values

### Example: cert-manager

```yaml
# infrastructure/controllers/cert-manager.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: cert-manager
---
apiVersion: source.toolkit.fluxcd.io/v1
kind: HelmRepository
metadata:
  name: jetstack
  namespace: cert-manager
spec:
  interval: 24h
  url: https://charts.jetstack.io
---
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: cert-manager
  namespace: cert-manager
spec:
  interval: 30m
  chart:
    spec:
      chart: cert-manager
      version: "v1.21.3"
      sourceRef:
        kind: HelmRepository
        name: jetstack
  install:
    crds: Create
  upgrade:
    crds: CreateReplace
  values:
    crds:
      enabled: true
    config:
      apiVersion: controller.config.cert-manager.io/v1alpha1
      kind: ControllerConfiguration
      enableGatewayAPI: true
```

Two things to note:

- **`crds.enabled`** replaces the old `installCRDs: true`, which is deprecated in current cert-manager charts.
- **`enableGatewayAPI`** lets cert-manager issue certificates for Gateway API listeners, not just Ingress objects. We use that below.

Pin chart versions exactly and let a bot like Renovate open the update PRs. This way upgrades become reviewable diffs instead of surprises.

## Taking Over Cilium

In Part 1 we installed Cilium by hand with `helm install`. That was necessary, because without a CNI there are no running pods, and without running pods there's no Flux. From now on, though, Cilium's configuration belongs in Git.

Flux's helm-controller uses the normal Helm release storage. If you create a `HelmRelease` with the **same name and namespace** as the existing release, Flux picks it up and runs an upgrade with the values from Git:

```yaml
# infrastructure/controllers/cilium.yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: HelmRepository
metadata:
  name: cilium
  namespace: kube-system
spec:
  interval: 24h
  url: https://helm.cilium.io/
---
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: cilium            # must match the release name from Part 1
  namespace: kube-system  # must match the namespace from Part 1
spec:
  interval: 30m
  chart:
    spec:
      chart: cilium
      version: "1.18.6"
      sourceRef:
        kind: HelmRepository
        name: cilium
  upgrade:
    remediation:
      retries: 3
  values:
    ipam:
      mode: kubernetes
    kubeProxyReplacement: true
    k8sServiceHost: localhost
    k8sServicePort: 7445
    securityContext:
      capabilities:
        ciliumAgent: [CHOWN, KILL, NET_ADMIN, NET_RAW, IPC_LOCK, SYS_ADMIN, SYS_RESOURCE, DAC_OVERRIDE, FOWNER, SETGID, SETUID]
        cleanCiliumState: [NET_ADMIN, SYS_ADMIN, SYS_RESOURCE]
    cgroup:
      autoMount:
        enabled: false
      hostRoot: /sys/fs/cgroup
    operator:
      replicas: 1
    hubble:
      relay:
        enabled: true
      ui:
        enabled: true
    gatewayAPI:
      enabled: true
      enableAlpn: true
      enableAppProtocol: true
      hostNetwork:
        enabled: true
    externalIPs:
      enabled: true
    l2announcements:
      enabled: true
    hostFirewall:
      enabled: true
```

> The values in Git **must match** what you installed by hand. Otherwise the first reconcile quietly reconfigures your CNI. Compare them first with `helm get values cilium -n kube-system`.
{: .prompt-warning }

> Your CNI is now managed by the same system that depends on it. A bad Cilium commit can break pod networking, and with it Flux's ability to roll the change back. Review Cilium changes carefully. If something goes wrong, `flux suspend helmrelease cilium -n kube-system` plus a manual `helm rollback` gets you out.
{: .prompt-danger }

The Gateway API CRDs from Part 1 can (and should) move into Git as well, for example as a Flux `GitRepository` pointing at the `kubernetes-sigs/gateway-api` release tag and a `Kustomization` that runs before `infra-controllers`.

## HTTPS with cert-manager and the Gateway API

With the controllers in place, the configs layer can use their CRDs. First, a Let's Encrypt issuer that solves HTTP-01 challenges through the Gateway:

```yaml
# infrastructure/configs/cluster-issuer.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: <YOUR_EMAIL>
    privateKeySecretRef:
      name: letsencrypt-account-key
    solvers:
      - http01:
          gatewayHTTPRoute:
            parentRefs:
              - name: public
                namespace: gateway
                kind: Gateway
```

Then the Gateway itself:

```yaml
# infrastructure/configs/gateway.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: gateway
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: public
  namespace: gateway
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
spec:
  gatewayClassName: cilium
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: All
    - name: https-app
      protocol: HTTPS
      port: 443
      hostname: app.example.com
      tls:
        mode: Terminate
        certificateRefs:
          - name: app-example-com-tls
      allowedRoutes:
        namespaces:
          from: All
```

Because we enabled `gatewayAPI.hostNetwork` in Part 1, Envoy listens directly on ports 80 and 443 of the node's public IP. You don't need a LoadBalancer service or an extra IP; just point your DNS record at the server.

cert-manager sees the annotation, creates a certificate for every HTTPS listener that has a `hostname`, and stores it in the referenced secret.

An app then only needs an `HTTPRoute`:

```yaml
# apps/talos-hetzner/my-app/route.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-app
  namespace: my-app
spec:
  parentRefs:
    - name: public
      namespace: gateway
      sectionName: https-app
  hostnames:
    - app.example.com
  rules:
    - backendRefs:
        - name: my-app
          port: 80
```

## Infrastructure vs. Apps

A simple rule of thumb for what goes where:

| Layer | Examples |
|-------|----------|
| `infrastructure/controllers` | Cilium, cert-manager, metrics-server, Longhorn |
| `infrastructure/configs` | ClusterIssuers, Gateways, IP pools, network policies |
| `apps/` | monitoring dashboards, code-server, internal services |

This separation:

- limits how much a single change can break
- makes refactoring easier
- gives you a natural rollout order

## Reconciliation & Drift Control

Flux continuously reconciles HelmReleases, plain manifests, and Kustomizations. If someone changes something by hand with `kubectl edit`, **Flux changes it back.** That's not a bug. It's GitOps doing its job.

Commands you'll use a lot:

```bash
flux get kustomizations          # is every layer Ready?
flux get helmreleases -A         # chart status across the cluster
flux reconcile kustomization flux-system --with-source   # don't wait for the interval
flux logs --level=error          # what went wrong
```

## The Disaster Recovery Story

This is where the whole setup pays off. If the server dies:

1. Install Talos again (Part 1, Steps 1–6).
2. Install Cilium by hand once (Part 1, Step 7), with the same values as in Git.
3. Run `flux bootstrap` again.
4. Wait.

Within minutes, Flux rebuilds every controller, every config, and every app from Git. You don't back up node configs, and you don't keep hand-maintained servers around. The only things you need to keep yourself are **persistent data** (volumes and databases) and **`secrets.yaml` from Part 1**.
